# Koyomi

An anime airing tracker with LINE reminders in Thai time (spec: `docs/specs/koyomi.md`, local-only). Next.js (App Router, TypeScript) with shadcn/ui, Tailwind v4 and MongoDB via Mongoose. The schedule sync, the public `/schedule` page, follows, the `/dashboard` week, LINE Login with `/settings`, the scheduled jobs with the daily LINE digest, the bot's `today` and `week` replies and the `/admin` status page exist; the GitHub repository and the working directory may still be named `nextjs-fullstack`.

## Commands (bun)

- `bun dev` — dev server. Needs MongoDB at `MONGODB_URI` (copy `.env.example` to `.env.local`).
- `./verify.sh` (`bun run verify`) — the baseline gate: format check, lint, typecheck, tests, build. Run it before claiming work is done.
- `bun run test` — Vitest. DB tests use `mongodb-memory-server`, so no local mongod is needed.
- `bun run e2e` — Playwright (Chromium) against a production build on port 3100 with an in-memory MongoDB; no local mongod or `.env.local` needed. First time on a machine: `bunx playwright install --only-shell chromium`. Tests live in `e2e/`, including an axe accessibility scan in both themes of `/`, `/schedule`, `/sign-in`, `/sign-up`, `/forgot-password`, `/verify-email` and `/reset-password` (with and without a token), and of `/dashboard`, `/settings` and `/admin` inside their journey tests. It is the contrast guard: add a new page to that list. The scan itself (`seriousViolations`, `scanBothThemes`) is in `e2e/axe.ts`.
- `bun run audit` — dependency vulnerability scan (needs network, so it is not part of `verify.sh`; CI runs it). Run it before adding or upgrading a dependency. It ignores one advisory, `GHSA-vfj7-8cjw-p6xm` (`braces@3.0.3`): no patched release exists and it is reachable only through build tooling (`shadcn`, `eslint-config-next`). Remove the `--ignore` when a fix ships.

## Gates (mechanical, do not bypass)

- Git hooks live in `.githooks/` and are enabled by `bun install` (`prepare` sets `core.hooksPath`). `pre-commit` blocks env files and secret-shaped strings, then checks formatting, lints the staged files and typechecks. `pre-push` runs `./verify.sh`, then the end-to-end tests.
- Never use `--no-verify`, `eslint-disable`, `@ts-ignore`, `@ts-expect-error`, `any`, or `!` to get past a gate. Fix the code. A genuine exception goes in `eslint.config.mjs` as a per-file override with the reason recorded here.
- Formatting is Prettier (width 100, Tailwind classes sorted). Run `bun run format` before committing; do not hand-format. Markdown and `handwriting-text.tsx` are ignored in `.prettierignore`.
- Lint fails on any warning. Typed rules are on: every promise is awaited, returned or explicitly `void`ed.
- `noUncheckedIndexedAccess` is on: `array[0]` is `T | undefined`. Handle the missing case; do not assert it away.
- `src/components` and `src/lib` must not import from `src/features` or `src/app` (lint-enforced). Features may import shared code, never the reverse.
- `bunfig.toml` installs exact versions that are at least 3 days old. Do not lower the cooldown to get a fresh release.

- CI (Continuous Integration) is `.github/workflows/ci.yml`: audit, `./verify.sh`, then the end-to-end tests, on every push to the default branch and every pull request. Actions are pinned to commit hashes; Dependabot (`.github/dependabot.yml`) proposes weekly grouped updates for the actions only: it cannot read this `bun.lock` (lockfile version 2). Package updates are manual: `bun outdated`, then `bun update <name>`, `bun run audit` and `./verify.sh`.
- `main` on GitHub is protected: no force push, no deletion, and pull requests need the `verify` check. The owner can still push directly; the `pre-push` hook is the gate for that path.

## Workflow (one ticket at a time)

1. Idea → `/grilling` until the open questions are settled.
2. Spec → `docs/specs/<feature>.md`.
3. Tickets → `.scratch/<feature>/issues/NN-<slug>.md`, each a vertical slice with checkbox acceptance criteria.
4. Implement one ticket test-first (`/tdd`): failing test, minimal code, refactor. Only one ticket is `in progress` at a time.
5. `./verify.sh` green → record the command and result in the ticket → `/code-review` → commit. One ticket per commit; the message names the ticket and what was verified.
6. UI tickets also need a recorded browser check before they are `done`.

## Layout

- `src/app` — routes. `/` is the landing page.
- `src/features/<name>` — one folder per feature (`auth`, `schedule`, `follows`, `line`, `notifications`, `admin`): `model.ts` (Mongoose), `schema.ts` (Zod), `service.ts` (DB logic), `actions.ts` (Server Actions), UI.
- `src/features/auth` — Better Auth. `auth.ts` builds the instance lazily (`getAuth()`); `session.ts` has the guards. Auth collections belong to the library, not Mongoose. Forms and buttons call the intent functions in `client.ts` (`signIn`, `signUp`, ...), which never reject and return a tagged outcome; Better Auth error codes, statuses and callback paths are named only there. Route paths live in `paths.ts`. Sign-in is email and password, plus LINE when it is configured (next item).
- **LINE Login** (`auth.ts`, `line-account.ts`, `line-errors.ts`, `line-button.tsx`) is registered only when both `LINE_LOGIN_CHANNEL_ID` and `LINE_LOGIN_CHANNEL_SECRET` are set; pages render the button from the server-side boolean `isLineLoginEnabled()`. Security rules, each pinned by a test in `auth.test.ts` that drives the real callback with LINE's token endpoint faked: LINE never reports an email as verified, so a LINE-supplied email gets no session until the emailed link is used (`requireEmailVerification`); a LINE sign-in never attaches itself to an existing account by email (`disableImplicitLinking`); connecting LINE is only ever explicit, from `/settings`, by a signed-in user (which is why LINE is a trusted provider there and its email may differ); the browser cannot hand over an ID token; a LINE profile without an email creates no account (the stand-in address in `auth.ts` only lets an already linked user sign in). Do not loosen one of these without its test.
- `src/features/line` — the app's side of LINE. `model.ts` has one `LineLink` row per linked user (LINE user id, friend flag, reminder slot); Better Auth reports a linked or signed-in LINE account through `onLineAccount`, but only while its user's email is verified (an unverified LINE sign-up gets no row and no reminder place), and `recordLineAccount` writes the row and asks LINE whether the user is a friend of the bot (`friendship.ts`). `service.ts` answers `areRemindersOn(userId)` (linked, friend, switched on, within the cap) and exports `listReminderRecipients()`, `findUserIdByLineUserId()` and `reminderPlaces()` (places taken against the cap, for `/admin`). The cap of ten is a unique index on the slot number, so there is no counter to race on; `ready()` creates the indexes. `webhook.ts` verifies `x-line-signature` before it parses anything and refuses every call while `LINE_MESSAGING_CHANNEL_SECRET` is unset; `lineEventHandlers` holds the friendship events (`follow`, `unfollow`); the `message` handler is added by `botEventHandlers()` in `src/features/notifications/bot-reply.ts`, which the Route Handler passes in, because `line` is the transport and must not import `notifications`. `/settings` is the UI; its three Server Actions are in `actions.ts`. The row is also removed by Better Auth's `account.delete` hook (`onLineAccountRemoved` in `auth.ts`), so an unlink that does not come through the action still ends the reminders. `messenger.ts` is the `LineMessenger` seam (`push(lineUserId, text, retryKey)` and `reply(replyToken, text)`, never throw, return `{ ok }`): the Messaging API over `fetch` (a 409 on a repeated retry key counts as sent), or with `USE_FAKES=true` `fake-messenger.ts`, which writes each message to the server log in a format it owns (`lineLog` read back by `pushesInLineLog`, `replyLog` by `repliesInLineLog`). Nothing calls `push` directly; see the quota guard below. A reply is free, is sent directly and is never retried (a reply token works once).
- `src/app/(auth)` — two route groups with their own layouts: `(split)` (sign-in, sign-up: brand panel beside the form) and `(card)` (verify-email, forgot-password, reset-password: centred card). `src/app/dashboard`, `src/app/settings` and `src/app/admin` are the protected areas; their layouts are `PrivateShell` (`src/features/auth/private-shell.tsx`) with different links. `src/proxy.ts` only checks that a session cookie exists.
- `src/lib/db/mongoose.ts` — cached connection (`connectDb`). Call it inside services, not at module top level. It also holds what every feature's models share: `defineModel` (reuse a model already compiled by a dev reload), `indexesReady(build)` (the `ready()` each service starts with: connect, then build indexes once per process) and `isDuplicateKey`. Do not re-implement these per feature.
- `src/features/schedule` — the airing schedule. `/schedule` is public (not in the proxy matcher) and is in the axe list of `e2e/auth.spec.ts`.
  - `day-window.ts` is the only place that knows a schedule day is 05:00 to 05:00 `Asia/Bangkok` (`dayWindowOf`, `weekRange`, `groupByDay`, `isScheduleDay`, `calendarMonthOf`, the Thai-time formatters, the parts of a day string, `formatWeekdayShort` and `dayOfMonth`, and `formatUntil(instant, now)` for "in 3 h 20 min", which rounds up so it says "now" only from the instant on). Every "today" or "this week" question goes through it; do not compute Thai dates elsewhere.
  - `source.ts` is the `ScheduleSource` seam: `animeschedule.ts` (AnimeSchedule.net API v3, throttled to one request per 600 ms) and `fake-source.ts` (invented shows placed relative to today). `USE_FAKES=true` selects the fake; the end-to-end server sets it. The real client has two fixtures: `fixtures/timetable.documented.json` is hand-written from the documentation (the edge cases), and `fixtures/timetable.recorded.json` is one week recorded from the real API on 2026-10-03, which the parser maps with nothing skipped. `bun scripts/record-animeschedule-sample.ts` records it again; its tests assert structure, not titles, so a new recording should pass unchanged. A source show carries `coverUrl` (or null). The real client builds it from the timetable's `imageVersionRoute`; the image host is named once, in `cover-host.ts`, which the client and the image allow-list in `next.config.ts` both read; a missing or odd-looking path gives null, never a skipped episode. The fake source points at invented covers in `public/images/fake-covers/` and leaves one show (`moss-and-thunder`) without one.
  - `service.ts` has no Next.js imports: `syncSchedule(source, now)` upserts shows and episodes keyed by the source's `route` slug and always records a run (a source failure such as a 429 is a `failure` record, not an exception); `episodesBetween(start, end, showRoutes?)` is the read every weekly view uses. Each entry carries its show's `coverUrl`; a show stored before covers existed gets one at the next successful sync, so there is no migration. Dates are stored as UTC; episodes expire 30 days after `airAt` through a TTL index. The connection does not buffer commands, so services call `ready()` (connect, then build indexes) before touching a model.
  - `poster-wall.tsx` is the public page's view: a sticky row of seven day links, then one labelled region per day with a grid of cover tiles (2, 3, 4 and 6 columns). A tile is the cover in a 2:3 frame through `next/image` (optimised, `alt=""`, the title is written below), the air time on a scrim block, and a scrim strip for `Following` and `Delayed`; a show without a cover gets its title on a muted tile. `next.config.ts` allows one remote image source, the cover host, so a cover from anywhere else is refused by the optimiser. `wall.ts` is the page's view model, a pure function with no Next.js or database imports: `posterWall(week, now, followed)` returns the days with `aired` and `followed` on each entry, the `upNext` entry (or null) and today's counts. A delayed episode is never aired and never up next, because it is not airing. Aired and up next depend on the hour, so they are tested there with an injected `now`, never end to end (the fake source follows the real clock) and never stored in the cached week. `up-next.tsx` is the block beside the page title; the cover next to it is the page's only eagerly loaded image. Aired tiles are greyscale and say `Aired`. `week-list.tsx` is the text list the dashboard still uses; `episode-label.ts` (`episodeLabel`, `delayNote`, `entryKey`) is shared by both. The day links carry `data-sticky-bar`, and `globals.css` gives the page a `scroll-padding-top` while such a bar exists, so neither a jump to a day nor keyboard focus lands under it: put the attribute on any other sticky top bar.
  - `sync.ts` is the Next.js side: `runScheduleSync()` syncs and expires the `schedule` cache tag, and `cachedWeekSchedule()` reads the public week through `unstable_cache`. Pages never call the source. `POST /api/dev/sync-schedule` triggers a sync; it answers only with `USE_FAKES=true` or under `next dev` and has no authentication, so never enable the fakes in production.
- `src/features/follows` — who follows which show (`follows` collection, unique on user and show route). Every service function takes the user id first and filters by it. `followedEpisodesBetween(userId, start, end)` is "what this user's shows air in a window"; `myWeek(userId, now)` feeds `/dashboard`, where a followed show is "Finished" once it has no episode left to air and the source says finished or the last successful sync no longer listed it. `actions.ts` holds the Server Actions (guard, Zod, service, `revalidatePath`). A signed-out Follow is a link built by `signInPathReturningTo`; the sign-in page reads the return path only through `safeReturnPath` in `src/features/auth/paths.ts`, the open-redirect guard.
- `src/features/notifications` — the scheduled jobs and the daily digest.
  - `queue.ts` is the `JobQueue` seam (`enqueue(job, payload, { deduplicationId })`): QStash publishes to `<BETTER_AUTH_URL>/api/jobs/<name>`; with `USE_FAKES=true` the in-process queue runs the job at once, and neither retries nor de-duplicates. `jobs.ts` holds the three jobs (`sync-schedule`, `digest-fanout`, `digest-send`), their Zod payloads, `runJob` and `jobQueue()`. `runJob` checks no caller: reach a job only through its Route Handler or the queue.
  - `job-route.ts`: every `src/app/api/jobs/<name>/route.ts` is one call to `handleJobRequest`. Order is fixed: 503 while `QSTASH_CURRENT_SIGNING_KEY` and `QSTASH_NEXT_SIGNING_KEY` are not both set (also with the fakes on; there is no unsigned mode), 401 unless the `Upstash-Signature` token verifies over the raw body, and only then the payload is parsed. Verification is the official `@upstash/qstash` `Receiver` (key, issuer, expiry, body hash, and the subject, which must be this job's URL built from `BETTER_AUTH_URL`, not `request.url`), always with `devMode: false`. A finished job answers 200 whatever its outcome; 500 only when a retry can help; 489 with `Upstash-NonRetryable-Error` for a bad payload. `test-helpers.ts` (`signJob`) signs calls for tests.
  - `digest.ts`: `fanOutDigest` (09:00) records every run in `digestruns`, skips when the last successful sync started more than 24 hours ago, and enqueues one `digest-send` per reminder recipient with a followed episode in today's window. `sendDigest` asks `findReminderRecipient` again, then claims the unique (day, user) row in `digestdeliveries` before pushing: `sending` (a 60 s lease), `sent` (final), `failed` or `refused` (may be claimed again). The LINE retry key is derived from (user, day), so a run that died between LINE accepting the push and recording it is repeated without a second message. `lastDigestRun()` is the read for the admin page.
  - `quota.ts`: `pushWithinQuota` is the only way a push leaves the app. One row per Bangkok month in `pushquotas`; a place is taken with a single conditional update (`count < 290`), keyed by the retry key so a repeat is not counted twice, and given back when the send fails. The 291st push returns `refused-quota` (a 200 to QStash, not a retry). `pushesThisMonth()` is the read. Replies are free and must not go through it.
  - `bot-reply.ts` answers a text message sent to the bot: `today` and `week` (any case, spaces trimmed) with the sender's followed episodes, anything else with a usage line, an unlinked sender with the link to `/settings`. Only a one-to-one chat with a reply token is answered. It sends through `LineMessenger.reply`, never through the quota guard; a failed reply is logged and dropped, and the webhook still answers 200. `reply-text.ts` owns the wording; `fitted` in `digest-text.ts` cuts an answer, and the digest, to LINE's 5000 characters.
  - `digest-text.ts` owns the episode line format (`episodeLine`, `digestText`); the bot's replies reuse `episodeLine`. `schedules.ts` lists the three QStash schedules; `bun scripts/create-qstash-schedules.ts` (`--dry-run` to print) creates them by fixed id, so it is safe to repeat. It has not been run against a real account.
  - `POST /api/dev/digest` runs the fan-out through the queue and answers only with `USE_FAKES=true`.
- `src/features/admin` — the `/admin` status page, for administrators only. `status.ts` (`adminStatus(now)`) is one read of the last sync, the last digest run with its delivery counts, the month's pushes and the reminder places; it writes nothing. Failure reasons pass through `redactSecrets` and are cut to 300 characters before they reach the page. `actions.ts` has `syncNowAction` (`requireAdmin()`, `runScheduleSync()`, `revalidatePath`). A regular user gets a 404 from `requireAdmin()`; the dashboard masthead links to `/admin` only for an admin.
- `e2e/schedule.ts` — helpers for tests: `syncSchedule` calls the dev route, and two helpers write to MongoDB directly (`.e2e/mongo-uri`) for what the UI cannot do. The journey test in `auth.spec.ts` holds the run's only real sign-in besides the three wrong-password attempts; put new signed-in checks inside it instead of signing in again.
- `e2e/` — `server.mjs` builds, starts MongoDB in memory and runs `next start`, writing the server log to `.e2e/server.log`. `outbox.ts` reads emailed links from that log through `linkInEmailLog` in `src/features/auth/email.ts`, which also owns the format the stub prints (`emailLog`); change the two together. Keep a log transport for tests when a real provider lands. Sign-in is rate-limited to 5 per minute per IP, so keep sign-in attempts per run under that.
- `src/lib/env.ts` — the only place that reads `process.env` (lint-enforced; tests are exempt). `dbEnv()` and `authEnv()` validate with Zod on each call and throw an error that names the variable, never its value. Add a new variable to its schema here and to `.env.example`.
- The LINE readers in `src/lib/env.ts` (`lineLoginEnv()`, `lineWebhookEnv()`, `lineBotEnv()`) never throw, because the app must run without LINE: they return `undefined` when their variables are unset. A half-set Login pair or a malformed bot ID is logged once, by variable name only. The same goes for `lineMessagingEnv()` (`LINE_MESSAGING_CHANNEL_ACCESS_TOKEN`: unset means every push fails by name) and `qstashSigningEnv()` (both keys or `undefined`). `qstashEnv()` (`QSTASH_TOKEN`, optional `QSTASH_URL`) throws by name and is only read when a job is published without the fakes. `appUrl()` is `BETTER_AUTH_URL`: the origin for job URLs and for links in messages. `redactSecrets(text)` replaces the value of every set secret variable (a name with SECRET, TOKEN, KEY or PASSWORD, and `MONGODB_URI`) with `[NAME]`, and URL credentials and bearer tokens with `[hidden]`: use it before showing text this app did not word, such as a library's error message.
- `e2e/server.mjs` forces the LINE and QStash variables to empty (a run can opt in with `E2E_`-prefixed ones), sets QStash signing keys that exist only there (`e2e/signing-keys.mjs`, so `e2e/digest.spec.ts` can show a job endpoint refusing an unsigned call and accepting a signed one), and leaves the database address in `.e2e/mongo-uri`; `e2e/seed.ts` uses it to write state no page can create (a linked LINE account). `e2e/settings.spec.ts` scans `/settings` in both themes inside its own journey; it signs up but never signs in, so it adds nothing to the sign-in budget. `e2e/digest.spec.ts` does the same: it seeds a linked user who follows today's shows, posts to `/api/dev/digest` and reads the message with `linePushes` from `e2e/outbox.ts`; it removes its LINE links afterwards because `settings.spec.ts` fills every reminder place. `e2e/admin.spec.ts` scans `/admin` in both themes, again with a sign-up and no sign-in: `ADMIN_EMAILS` is empty on the end-to-end server, so `makeAdmin` in `e2e/seed.ts` sets the role on the `user` row (the session reads it on every request), and `seedFailedSync` records a failed sync, which the fake source cannot produce. It saves screenshots to `.e2e/screenshots/`.
- `src/components` — shared components that are not shadcn: `masthead.tsx` (the top strip of every page), `brand.ts` (the product name and shared brand copy; the root layout builds page titles from it as `<page> · Koyomi`), `text-link.tsx`, `theme-toggle.tsx`, `status-row.tsx` (the label and state rows of `/settings` and `/admin`), and `motion/` (see Motion below).
- `src/components/ui` — shadcn components. Add more with `bunx --bun shadcn@latest add <name>`.

## Conventions

- Validate all input with Zod at the Server Action / Route Handler boundary.
- Server Actions write; Route Handlers are for external clients.
- Every private page and Server Action starts with `requireSession()` or `requireAdmin()` from `src/features/auth/session.ts`. `src/proxy.test.ts` checks pages for a forgotten guard (a text check, not proof that the call comes first): every page under a path in the proxy's matcher must await a guard, and every page that awaits one must be under the matcher, so add a new private area to the matcher in `src/proxy.ts`. Server Actions are not checked yet. Roles (`user`, `admin`) are set once at account creation from `ADMIN_EMAILS`.
- Colour, type and shape come from the design system below. Use semantic classes (`bg-card`, `text-muted-foreground`), not raw colors.
- `src/features/auth/email.ts` is a stub that logs the email instead of sending it; its `no-console` exception in `eslint.config.mjs` goes away when a real provider lands. `src/features/line/fake-messenger.ts` has the same exception for the same reason: the log is its transport.
- `src/components/ui/handwriting-text.tsx` is a third-party component with one local addition, the `accent` / `accentClassName` props (the landing page colours "LINE" with `text-line`); re-apply it if the component is ever replaced from upstream. Its lint exceptions are in `eslint.config.mjs`. The landing page self-hosts its font at `public/fonts/handwriting.ttf` (the default CDN font is blocked by CORS). It still loads opentype.js from a CDN at runtime and falls back to plain text if that fails.

## Design system (Linen Editorial)

The brand as a printed magazine: warm paper, ink text, one terracotta voice. Decision and token table: `docs/specs/linen-editorial-design-system.md` (local-only).

- **Tokens** (oklch, light and `.dark`) live in `src/app/globals.css`; `--radius` is `0px`. Primary is terracotta in light, clay in dark; the label on it is `primary-foreground`. Do not put opacity on text (`text-primary-foreground/70` failed contrast); pick a token.
- **Type**: `font-display` (Instrument Serif, regular or italic, never bold) for page titles and card titles, with at most one italic `text-primary` word in a hero. Body text is Google Sans Flex. Labels and buttons are Google Sans Code through the `label-mono` utility (defined in `globals.css`).
- **Shape**: square corners; structure is drawn with rules (`border-foreground` for major edges, `border-border` between rows), not rings or shadows. Fields are underlined, cards have a 1px `foreground` outline. Button sizes: `xs` 24, `sm` 32, default 40, `lg` 44 px; use `size="lg"` for a form's main action. There is no `large` input variant.
- **Layout**: every page opens with `Masthead` (pages pass their actions as children). `HandwritingText` is the single decorative accent, at most one per screen, on the terracotta panel. On the landing page that panel is a blurred poster (`public/images/landing-poster.jpg`) under an ink scrim instead of terracotta: text there uses `bg-scrim` / `text-scrim-foreground`, which are the same in both themes. `text-line` is LINE's brand green and only passes contrast on the scrim; never use it on paper. axe cannot measure contrast over an image, so check that panel by eye when the image or scrim changes. The same rule holds on the schedule's cover tiles: text over artwork always sits on a `bg-scrim` block, never on the image itself.
- **Motion**: quiet, ease-out, no spring or bounce, built on the `motion` package. Spec: `docs/specs/motion.md` (local-only).
  - `src/components/motion/tokens.ts` is the only place for durations, easing, travel, stagger and press scale; do not hard-code those numbers elsewhere.
  - Pages and layouts stay Server Components: wrap content in the small client wrappers `Reveal` (mount or `inView`, `slideOnly` for content that must be visible from first paint), `Stagger`/`StaggerItem`, and `PresenceMessage` (an appearing error or notice). Keep the live region (`role="alert"` or `"status"`) outside `PresenceMessage` so it stays mounted. Use the `m` components, never `motion.*`: `LazyMotion` is `strict` in the root `MotionProvider`.
  - Every wrapper element carries `data-arrive`, and `globals.css` forces its final state under `prefers-reduced-motion`. `motion` itself only applies transforms instantly in that mode, so keep the attribute and the rule in step; `Button` drops its press gesture with `useReducedMotion`.
  - Opacity is only animated during an arrival and ends at 1; never put opacity on resting text. No hover scale, no shadow, no motion on `Masthead` or `HandwritingText`, no page transitions.
  - `src/components/ui/button.tsx` is a locally edited shadcn component (press feedback, narrowed `transition`); `shadcn add button --overwrite` would drop the edits.
  - Tests: Playwright runs with reduced motion on, so scans read final-state content. `e2e/motion.spec.ts` is the one place that lets animations play. Its checks measure the opacity compounded up the ancestors, not the element's own, and each new wrapper needs a case there. Prove a new guard bites by forcing the end state to 0.5 for a run.
